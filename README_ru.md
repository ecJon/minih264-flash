## 📖 Введение

**minih264-flash** — это форк проекта [lieff/minih264](https://github.com/lieff/minih264): превосходный минималистичный кодер H.264/SVC в виде библиотеки из одного заголовочного файла на переносимом C (с опциональными SIMD-путями SSE/NEON), переданный в общественное достояние (CC0). Вся архитектура и дизайн кодера — заслуга автора оригинала; этот проект просто стоит на плечах этой работы.

Опираясь на этот прочный фундамент, этот форк переносит горячие участки кодера в **векторный блок EE** ESP32-S3 в виде рукописного ассемблера Xtensa — кодирование полного 720p-кадра падает с ~2400 мс до **263 мс, в ~10 раз быстрее**. Каждый kernel проходит **побитовую A/B-проверку** на совпадение с эталоном на C — SIMD-путь меняет *скорость*, но не *результат*.

> ⚠️ Как и в оригинале, код сильно экспериментальный: сложность кодера сознательно обменяна на размер и скорость (см. [Ограничения](#-ограничения)).

## ✨ Возможности

- 📄 **Один заголовок, ноль зависимостей** — достаточно `#include "minih264e.h"`
- ⚡ **Векторный блок EE ESP32-S3** — 5 самых горячих kernel'ов (прямое преобразование, квантование, реконструкция, SAD, копирование строк) перенесены на 128-битный векторный ассемблер; ~94% кода остаётся на C
- 🔁 **C всегда остаётся запасным путём** — у каждого ассемблерного kernel'а есть чисто C-близнец; `-DH264E_FORCE_PLAIN_C` отключает ассемблер на этапе компиляции (C-бэкенд к тому же служит побитовым эталоном A/B-проверки)
- 🎯 **Архитектура P-skip** — настраиваемая полоса строк MB принудительно кодируется как skip (кодирование области изменений): статичный UI-кадр стоит **~34 мс / 30 байт** вместо полного I-кадра
- 🧵 **Двухпотоковое кодирование** (MT на 2 полосы) с последовательным резервным пулом
- 🔧 **Хуки времени выполнения** — `h264e_sps_id`, `h264e_log2_max_frame_num_minus4`, переключатель сегментного профилирования
- 🆓 **Лицензия CC0** — использовать, изменять, продавать; указание авторства не требуется

## 📊 Производительность

ESP32-S3 @ 240 МГц · 1280×720 · полный I-кадр:

| | эталон C @ 160 МГц | **minih264-flash @ 240 МГц** |
|---|---|---|
| время кодирования | ~2400 мс | **263 мс (в 9,1 раза быстрее)** |
| объём | — | один заголовок + рукописный ассемблер |

Цепочка P-кадров (режим области изменений, статичный UI-подобный контент): **~34 мс / 30 байт** на статичный кадр; кодирование полного кадра ~263 мс.

> Сравнение с x264 на x86 (скорость, размер, PSNR) — см. [README оригинала](https://github.com/lieff/minih264#comparison-with-x264).

## 📦 Быстрый старт

### Компонент ESP-IDF

Скопируйте этот репозиторий в свой проект как `components/minih264` или подключите как submodule — входящий в комплект `CMakeLists.txt` автоматически регистрирует ассемблерные kernel'ы Xtensa:

```bash
git submodule add https://github.com/ecJon/minih264-flash.git components/minih264
```

### Сборка на хосте (эталон / A/B-тесты)

На macOS/Linux собирайте с `-DH264E_FORCE_PLAIN_C`, чтобы принудительно использовать чистый C-бэкенд — весь конвейер воспроизводим без устройства.

### Запуск демо

```bash
cd demo
make test        # каноничный A/B-гейт: SIMD-бинарник vs бинарник на чистом C,
                 # битовые потоки побайтно сравниваются через cmp(1)
./minih264_demo  # трёхфазный клип (движение / статика+P-skip / движение)
                 # -> out.h264 (Annex-B); проигрывание: ffplay out.h264
```

Пример для ESP32-S3 лежит в `examples/idf_demo` (ESP-IDF v5.x):

```bash
idf.py set-target esp32s3
idf.py -p PORT build flash monitor
```

Он кодирует тот же клип **на самом чипе** (160x120, работает без PSRAM), а затем запускает A/B-гейт на устройстве: ассемблер Xtensa EE против чистого C, переключение в рантайме через `H264E_select_backend`.

## 🚀 Использование

```c
#include "minih264e.h"

H264E_create_param_t par = { 0 };
par.width  = 1280;
par.height = 720;
par.gop         = 30;   /* цепочка P-кадров */
par.max_threads = 2;    /* многопоточность на 2 полосы */

int szp, szs;
H264E_sizeof(&par, &szp, &szs);
H264E_persist_t *persist = malloc(szp);
H264E_scratch_t *scratch = malloc(szs);
H264E_init(persist, &par);

H264E_run_param_t rp = {
    .encode_speed = 9,          /* максимальная скорость */
    .qp_min  = 12,
    .qp_max  = 24,
    .desired_frame_bytes = 40000
};
H264E_io_yuv_t in = {
    .yuv    = { y_plane, u_plane, v_plane },   /* I420 */
    .stride = { 1280, 640, 640 }
};
unsigned char *coded; int coded_len;
H264E_encode(persist, scratch, &rp, &in, &coded, &coded_len);
/* `coded` действителен до следующего вызова H264E_encode */
```

### Кодирование области изменений (P-skip)

```c
/* Строки MB [y0, y1) принудительно кодируются как skip: без потерь
 * копируются из опорного кадра (стоимость≈0, skip_run).
 * Строка y1 — защитная строка деблокирующего фильтра. */
extern int h264e_skip_y0, h264e_skip_y1;   /* полоса строк MB, глобальная */

h264e_skip_y0 = 20;
h264e_skip_y1 = 31;

/* ... кодировать как обычно через H264E_encode(...) */
```

### Настройки, специфичные для форка

| символ | значение |
|---|---|
| `h264e_sps_id` | id SPS в генерируемом потоке (имитация чужого потока vs собственный) |
| `h264e_log2_max_frame_num_minus4` | разрядность frame_num |
| `h264e_skip_y0 / h264e_skip_y1` | принудительная полоса P-skip `[y0, y1)` (см. выше) |

## ✅ Методика верификации

Каждый ассемблерный kernel должен пройти **побитовую A/B-проверку**: один и тот же входной кадр кодируется один раз C-бэкендом и один раз Xtensa-бэкендом, после чего оба битовых потока сравниваются побайтно. Сборки на хосте используют `-DH264E_FORCE_PLAIN_C`, поэтому эталонная часть проверки работает где угодно. Гейт воспроизводим на любом хосте командой `cd demo && make test`; пример для ESP32-S3 выполняет тот же гейт на чипе через `H264E_select_backend`.

## 🌍 Поддерживаемые платформы

| бэкенд | статус |
|---|---|
| ESP32-S3 Xtensa + векторный ASM EE | production |
| чистый C (любые 32-бит+ MCU / хост) | эталон & A/B-проверка |
| x86 SSE / ARM NEON из оригинала | унаследовано (в этом форке не тестировалось) |

## ⚠️ Ограничения

Унаследованы от оригинала — по сравнению со сборкой x264 *baseline*, minih264 не реализует:

- квантование Trellis
- выбор режима предсказания на основе SATD
- компенсацию движения 4×4

Кроме того, бэкенды x86 SSE / ARM NEON из оригинала переносятся без изменений, но **в этом форке не тестировались**.
